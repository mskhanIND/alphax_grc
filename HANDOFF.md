Paste the prompt at the bottom of this file into Claude Code (or any capable coding agent) with this repo open.

## 1. What is being built
IRSAA wants the existing `ia_maturity` React prototype (github.com/mskhanIND/ia_maturity) turned into a real
GRC & Audit platform on Frappe. The prototype has no backend and fake login, so this repo (`alphax_grc`) is a
proper Frappe v15 app that reuses its content, scoring maths and layouts.

Decisions already made (do not reopen without the owner):
- Frappe v15, **new site**, **single site and single database**, customers isolated by Organization.
- Host inside Saudi Arabia (PDPL). Domain grc.muftaah.com or alphaxerp.com, to be confirmed.
- Release 1 = ONE complete journey: public site -> register + email verification -> organization setup ->
  20-question assessment (autosave/resume, evidence) -> submit -> GRC assignment + review + clarification ->
  approval -> approved scorecard + PDF. Plus reminders, follow-up tracking, org access controls.
- Control catalog, risk, asset risk, compliance, audit actions, security operations = Phase 2+, only leave room.
- Staff workspace is built in **Frappe Desk** (not React). Customer portal + public site are plain server-rendered
  www pages plus vanilla JS (no Node build, so install never depends on yarn).
- Scoring is **server-side Python**; the browser never produces an official result.
- Template policy defaults in v1.0 follow the Excel reference: equal weights, **no Q1 cap, no Q20 N/A**, Q13 manual.
  The prototype had Q1 cap ON and Q20 N/A ON; those are OPEN decisions for the assessment owner. They are
  per-template-version switches (`enable_gating`, `allow_na`) so they can change by publishing v1.1.
  Calculated Q13 (from an issue register) is deferred to Phase 2.

## 3. Sandbox lessons (so you do not lose time)
- `bench` refuses to run as root: create a non-root user (`frappe`) and run bench as that user.
- Frappe v15 needs Python 3.10-3.12 (system python 3.13 is too new): use /usr/bin/python3.11 or uv.
- Through a proxy, `yarn install` failed; backend work does not need JS assets. `bench init --skip-assets`.
- Redis ports used: cache 13000, queue 11000, socketio 12000 (see `sites/common_site_config.json`).
- Background processes die between turns; `dev/start_services_sandbox.sh` restarts MariaDB + Redis.
- Install loop: `bench --site test.localhost install-app alphax_grc` then `bench --site test.localhost migrate`.
  When editing DocType JSON by hand, bump `modified`, otherwise migrate skips it (the generator does this).
- Frappe class/file naming: DocType "GRC Follow Up Log" -> `grc_follow_up_log.py`, class `GRCFollowUpLog`.
  Avoid hyphens in DocType names.

## 4. Build plan, in order (verify each step on the test site before moving on)

### 4.1 Foundations
1. `hooks.py`: `required_apps`, `after_install`, `after_migrate`, `scheduler_events` (daily), `role_home_page =
   {"GRC Customer": "grc"}`, `permission_query_conditions` and `has_permission` for GRC Assessment, GRC Organization,
   GRC Clarification, GRC Follow Up Log, GRC Reminder, GRC Report.
2. `grc/install.py`: create roles **GRC Customer** (desk_access=0), **GRC Consultant**, **GRC Reviewer**,
   **GRC Manager** (desk_access=1); set Website Settings `disable_signup=1` and `home_page="grc-home"`; import
   template v1.0 from `dev/prototype_data/template.json` (move a copy to `alphax_grc/data/`), seed 5 frameworks
   (status Published, `reviewed_on` blank so the site shows "review pending"), set GRC Settings defaults,
   Number Cards, workspace. Add `create_demo_staff()` runnable via `bench execute` that makes a consultant,
   reviewer and manager with random passwords printed to the console.
3. `grc/access.py`: `get_membership(user)`, `is_manager/is_staff`, the query-condition and has_permission functions.
   Managers and System Manager see everything. Consultants and reviewers see only assessments where
   `assigned_consultant` or `reviewer` is them (and the organizations and child records behind those).
   Anyone without a staff role gets `1=0` / False.

### 4.2 Scoring (pure Python, no frappe import, unit-tested)
`grc/scoring.py::compute(snapshot, answers)`; port `src/utils/scoring.ts` from the prototype repo exactly:
- points A25 B50 C75 D100 from the snapshot; unanswered counts in the denominator; N/A removes the question from
  the denominator only when `snapshot.allow_na` AND `question.allow_na`.
- section % = points/max rounded to 1 decimal; overall = total points / total max, or the section-weighted mean when
  `weighting_method == "Section Weights"`.
- bands: highest band whose `min_score <= pct`. Defaults: <35 Critical, <55 Low, <75 Medium, <90 High, >=90 Leading.
- gating cap only when `snapshot.enable_gating` and the question is gating and the answer matches `gate_trigger`.
- findings/actions for answers A/B/C: priority Immediate (0-3 months) / High (3-6) / Medium (6-12); recommended
  action = the next level's option text. Return everything needed for the scorecard and PDF, EN and AR.
- Tests in `alphax_grc/tests/` must include fixtures that reproduce the Excel results (all-C = 75% High, mixed
  answers, N/A and gating on/off, unanswered counted as zero).

**Version snapshot rule:** creating a GRC Assessment copies the whole template version (policy, sections,
questions, bands) into `template_snapshot` JSON; scoring and the portal read ONLY the snapshot. A Published or
Retired GRC Template Version cannot be edited (only Published -> Retired) and cannot be deleted if used.
Add form buttons: Publish, New Version (clone to Draft).

### 4.3 Assessment workflow
Implemented as a state machine in code, not the Frappe Workflow doctype, because customers transition through the API.
Draft -> In Progress -> Submitted -> Under Review -> Clarification Required -> Resubmitted -> Under Review ->
Approved -> Report Released. Rules:
- Draft -> In Progress on first save of answers. Submit needs all 20 answered; it freezes `preliminary_*` and stamps
  `submitted_on`. Resubmit refreshes preliminary results and increments `resubmit_count`.
- Staff actions (whitelisted `staff_action(name, action, note)` plus Desk form buttons): start_review (consultant,
  reviewer, manager; auto-assigns the actor if unassigned), request_clarification (creates a GRC Clarification
  Request and emails the customer), approve (Reviewer or Manager only; blocked while any clarification is Open;
  computes `final_*` from `reviewer_option` falling back to `selected_option`; sets Answered clarifications to
  Resolved), release (Manager only; generates Approved PDFs en+ar into GRC Report as private Files; emails the
  customer), reopen (Manager, Approved -> Under Review). Report Released is immutable.
- `status` is read-only in Desk; block any status change that does not go through the transition function.
- Customers see: status, required next action, the **Preliminary** score after submit, and the **Approved**
  scorecard and PDF only after Report Released. Never expose reviewer notes, `reviewer_option`, internal notes or
  any other organization's data.

### 4.4 Customer APIs: `alphax_grc/api/portal.py`
**Security model: customers have NO DocType permissions at all.** Every customer call goes through a whitelisted
method that resolves the caller's active GRC Organization Member, checks the org role, and then reads or writes with
`ignore_permissions=True`. Wrong-org and missing records return the same generic "not found" error. Evidence is NOT
served through Frappe's file routes; use our own endpoints.

Guest endpoints (`allow_guest=True`, rate limited with `frappe.rate_limiter.rate_limit`, no account enumeration):
- `register_start(email, full_name, invite_token=None)`: validate work email (GRC Settings block/allow lists), send a
  6-digit code (store only a hash in cache, TTL from settings, max attempts).
- `register_verify(email, code)` -> returns a short-lived `reg_token` bound to the email.
- `register_complete(email, reg_token, password, language, org={legal_name, sector, city, ...})`: NO User exists
  before this point. Creates the Website User (role GRC Customer), then either creates the GRC Organization with an
  Org Admin membership (first user) or, with a valid invitation for that email, joins that org with the invited
  role. Logs the user in. Password policy: at least 10 characters, a letter and a digit.
- `invitation_info(token)`, `submit_consultation(...)` (honeypot + rate limit), `site_config()`.

Signed-in endpoints: `get_context`, `create_organization`, `accept_invitation(token)`, `get_organization`,
`update_organization`, `list_members`, `invite_member`, `revoke_invitation`, `change_member_role`, `remove_member`
(never remove or demote the last Org Admin), `list_assessments`, `start_assessment`, `get_assessment` (snapshot
questions + own answers + evidence + clarification threads + permission flags), `save_answers` (autosave; validate
options; editable only in Draft / In Progress / Clarification Required), `submit_assessment`, `resubmit_assessment`,
`upload_evidence` (multipart; size and extension allow list from settings; private File with `attached_to_field` =
question code), `delete_evidence`, `download_evidence` (streams after the org check), `add_clarification_reply`,
`get_scorecard`, `download_report(name, kind, lang)` (preliminary generated on the fly with a PRELIMINARY watermark;
approved only after Report Released), `dashboard`, `set_language`.
Org roles: Org Admin (all), Assessor (answer, submit), Action Owner and Viewer (read only).
Invitation tokens: random, store only the SHA-256 hash, 7-day expiry, bound to the invited email.

### 4.5 Customer portal (no build step)
`www/grc/index.html` + `index.py`, assets in `public/css` and `public/js`, hash routing (`/grc#/dashboard`), EN/AR
with RTL. Screens: sign in; register (details -> code -> password + organization or invitation); dashboard (next
action, progress, latest scorecard); assessments list; take-assessment (6-section stepper, A-D option cards with
level names, comment, evidence upload, debounced autosave with a "saved" indicator, read-only once submitted,
clarification panel, resubmit); scorecard (overall + section bars + level, Preliminary vs Approved badge, gating
note, gaps and recommendations, PDF buttons, disclaimer); organization (profile, members, invitations); settings
(language, change-password link to `/update-password`, sign out). The sidebar also lists Control Catalog, Risk,
Asset Risk, Compliance, Audit Actions and Security Operations as disabled "Phase 2". Reuse layouts and strings from
`dev/prototype_data/i18n.json` and the prototype's teal/blue AlphaX look.

### 4.6 Public website
Pages `grc-home`, `grc-assessments` (catalogue from GRC Assessment Template where `show_on_website`),
`grc-frameworks` (published GRC Framework with a sector filter and an "applicability review pending" badge when

### 4.7 GRC Desk workspace
Workspace "AlphaX GRC" with shortcuts and Number Cards (Awaiting review, Under review, Clarification pending).
Form JS: GRC Assessment buttons per status and role, GRC Organization buttons ("Invite admin", "Assign
assessment"), GRC Template Version (Publish, New Version), list-view status indicators. Script Reports:
**GRC Survey Tracker** (not started / in progress / submitted per customer, overdue flag, last follow-up) and
**GRC Consultant Workload** (open reviews per consultant, overdue reviews).

### 4.8 Reminders and notifications
Daily scheduler: send due GRC Reminder rows; automatic reminders for Draft / In Progress assessments N days before
the due date and every X days when overdue (GRC Settings); clarification SLA reminder; manager digest of reviews
older than the review SLA. Every automatic send writes a GRC Follow Up Log (type System Reminder). Emails in EN/AR to
the respondent and Org Admins. Wrap every send so a missing outgoing email account never breaks a user action; test
what `frappe.sendmail` does on a site with no email account and decide how the registration code reaches a tester
(the settings flag `show_code_when_email_unavailable` exists for TEST sites only).

### 4.9 PDF report
`frappe.utils.pdf.get_pdf` from a Jinja template; embed Noto Sans Arabic as a base64 @font-face; RTL for Arabic;
cover (org, template version, dates, Preliminary or Approved), executive summary, section scores (CSS bars, not JS
charts), findings and actions, scoring method, disclaimer from GRC Settings ("does not imply regulatory compliance
or certification"). Render to PNG (pdftoppm) and LOOK at the Arabic page before calling it done.

### 4.10 Tests and acceptance
- Unit: scoring parity; state machine; invitation and registration rules; password policy.
- **Cross-organization isolation suite (release gate):** two orgs; try every portal endpoint, evidence download and
  report download with the other org's names and ids; all must fail with the generic error. Also confirm a
  GRC Customer cannot read any DocType via `/api/resource`.
- End-to-end on the test site: register -> verify -> org -> assessment -> evidence -> submit -> staff assign ->
  start review -> clarification -> resubmit -> approve -> release -> customer downloads the Approved PDF.
- Staff scoping: consultant B cannot open consultant A's assessment.
- Ship `README.md` install steps: `bench get-app`, `bench --site <site> install-app alphax_grc`,
  `bench build --app alphax_grc`, enable scheduler, configure outgoing email, GRC Settings, create staff users.
